## 2026-09-17 Bug 修复：关详情后列表位移 + 滚动时条目跳动

**BUG-1（社交媒体视图关掉详情后列表像自己往上滚）——已修，实测位移 0。**
根因：桌面社交视图里「详情 / 列表」是同一个插槽的二选一
（`content={selectedEntryId ? <详情/> : <EntryList/>}`），点开条目会**整块卸载** `EntryList`，
关闭时重新挂载，滚动位置只能靠模块级 `entryListScrollPositions` 还原 —— 看起来就是「自己往上滚了」。
移动端那段早就写成「列表保持挂载以保留状态」（代码注释就是这么写的），桌面社交分支没有跟上。
修法：与移动端对齐，列表常驻、详情盖在上面（`absolute` + `inert` + `aria-hidden`），并给列表传 `isActive={!selectedEntryId}`
（否则详情打开时滚动已读/快捷键仍在后台跑）。
实测：开详情前 / 详情打开时 / 关闭后三次采样 —— 卡片数 50→50→50、首个可见条目 id 相同、`top` 148→148→148，**位移 0**。

**BUG-2（向下滑再往回滑时条目跳动）——两条机制，都已处理。**
- 机制一：已读态把标题从 `font-semibold` 切成 `font-medium`。字重一变，同一条标题的换行数就可能变（1 行 ↔ 2 行），
  卡片高度随之变化；滚动标记已读时整列重排，就是一次跳动。
  对照 Nextflux 的 `ArticleCard`：它**字体恒为 `font-semibold`，只用颜色区分读态**（`text-muted` / `text-foreground`）。
  已按它对齐，并补回归测试（jsdom 没有 Tailwind CSS，量不到 computed style，所以断言类名）。
- 机制二：社交卡片正文是 `inView` 门控的（进视口前挂载，挂载后最多按 300px 折叠高度撑开）。
  向下滚时新卡在**下方**挂载，撑开不影响可见内容；向上滚时卡片是在**上方**挂载的，撑开会把可见内容整体推下去 ——
  正是用户描述的「往下滑、再往上滑的时候跳」。改成非对称 rootMargin `2000px 0px 1000px 0px`（上方两屏），
  让上方卡片在用户回滚之前就挂载好；代价是多挂载几张卡（约 3000px 内容）。
- **诚实标注**：机制二属于机制性修复，本轮**未能用脚本复现**出跳动（可复现的前提恰恰是 BUG-1 的「列表被卸载重挂」），
  因此这条等你实机验证；若仍有跳动，下一刀上「移除卡片时按其实测高度补偿滚动」
  （`useScrollMarkRead` 里已有 `scrollBy(-removedHeight)` 的补偿，但高度是估算值，可能不准）。

## 2026-09-17 第九批第 8 刀：自动化顺序改成拖动（第 8 项）

**做法**：用项目里已有的 `framer-motion` `Reorder`（外观页的「内容分类」排序也是这套），规则列表换成

## 2026-09-17 第十批第 5 刀：星标加「只显示当前视图」一档（10-11）
