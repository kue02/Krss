## 一、结论先行

1. **Folo 没做这件事**——它的 MCP 只是「给 AI 装工具」，与订阅/条目零关系。所以「照抄 Folo」不存在，参考价值只在**连接层的形状**（下面给了它的类型契约）。
2. 入向的真正难点是 **MCP 的返回值没有固定形状**，而条目有固定形状 —— 中间必须有一层**声明式映射**。
   但**不是「每个 MCP 都要手工映射」**：按返回值可以分四档，前三档基本自动（见 §三）。
3. 出向（Krss 当 MCP 服务器）与入向**共用同一套底座**（一份连接/协议实现），且入向的「映射」问题在出向不存在——因为我们自己控制返回形状。

## 三、入向：MCP → 条目，映射到底要多少人工？

依据 **MCP 规范 2025-06-18**（`server/tools`、`server/resources`）：

- `tools/list` 返回的工具定义里，`inputSchema` 必有、**`outputSchema` 可选**（JSON Schema）；
- `tools/call` 的结果 = `content[]`（`text` / `image` / `audio` / `resource_link` / `resource`）+ 可选 **`structuredContent`**（JSON 对象，与 `outputSchema` 配对）；
- 规范还让「返回结构化内容的工具**同时**把 JSON 序列化进一个 `TextContent`」以兼容旧客户端（← 这条对我们很关键）；
- 另外 MCP 还有 **resources**：`uri` + `mimeType` + `text` + 可选 `lastModified`。

**四档自动度**（这才是「要不要每个都手工映射」的答案）：

| 档 | MCP 返回什么 | 我们要做多少 | 自动化程度 |
|---|---|---|---|
| **1. 资源型** | `resources/list` 或 tool 返回 `resource` / `resource_link`（带 `uri` + `mimeType` + `lastModified`） | 几乎不用映射：`uri`→去重键+链接、`name`→标题、`text`→正文 | **全自动** |
| **2. 带 `outputSchema`** | 工具声明了输出 schema | **读 schema 直接生成映射**（properties 里 title/url/date 一眼可辨） | **全自动** |
| **3. 有 `structuredContent`、无 schema** | JSON 结构但没声明 | 按常见字段名**自动预填**（title/name/subject、url/link、content/body/description、published_at/created_at/updated_at、id/key/slug），人扫一眼确认 | **半自动（秒级）** |
| **4. 只有纯文本** | `content[0] = {type:"text", text:"..."}` | 先尝试把 text 当 JSON 解析（规范本来就这么建议）→ 命中则退回 2/3 档；不是 JSON 则按 Markdown 标题/列表切分；都不行才需要**人来指或 AI 来猜** | **人工 / AI** |

**所以答案是**：不是每个 MCP 都要手工映射——**第 1~3 档基本自动**，只有「纯文本且非 JSON」那档才真的需要人工或 AI。
配套两个降低重复劳动的设计：
- **映射存成预设**（同一个 MCP 复用；也能导出/内置几个热门 MCP 的映射）；
- **建源时就预览前 5 条**（映射对不对一眼可见，避免「建完发现标题全是空」）。

## 四、入向方案骨架

### 4.1 数据模型

| 落点 | 内容 | 迁移 |
|---|---|---|
| `feeds` 加两列 | `source_type TEXT`（`rss` 默认 / `mcp`）、`mcp_config TEXT`（JSON：连接 id + 工具名 + 参数 + 字段映射 + 去重键） | **27**（26 已被代理那批预定） |
| 新表 `mcp_servers` | `id, name, transport, url, headers, enabled, is_connected, last_error, tool_count, resource_count, created_at, updated_at` | 同一次迁移 |
| 老数据 | 新列默认 `rss` / NULL ⇒ **行为零变化** | `addColumnIfMissing` |

取舍依据（本项目既有规矩）：**多字段聚合 → KV；需要按维度索引/遍历/统计的实体 → 新表**。MCP 连接有连接状态、错误、计数，且要被「建源向导」遍历与引用 ⇒ **建新表**（用户已拍板按推荐）。

### 4.2 执行时序（关键：分叉点放在写库之前）

```
刷新／添加订阅
  └─ 按 feeds.source_type 分叉
       ├─ rss：原样（HTTP + gofeed 解析）
       └─ mcp：连服务 → 调工具/取资源 → 按映射生成 []model.Entry
  └─► 汇合到既有的 saveEntries()   ← 之后一切不用改
        去重(hash 唯一索引) / FTS / 规则引擎 / 自动翻译标记 / 未读计数
```

**两条入库路径都要接**（本项目铁律）：刷新走 `refresh_service.saveEntries()`；「添加订阅」的第一批是 `feed_service.Add()` 自己写库 —— MCP 源创建时要能立刻拉一次。

### 4.3 去重键（用户问的第 4 条，其实不用你操心）

RSS 侧**已经有现成的退化顺序**，MCP 照抄即可（`feed_service.go:766` 的 `computeEntryHash`）：

```
GUID → 链接(link) → 标题 + 内容
```

MCP 版对应：

```
映射里指定的键字段（id / key / slug / url）→ 条目的链接字段 → 标题 + 时间
```

- 前两级是**稳定唯一键**，重复取回不会重复入库；
- 最后一级只在「MCP 什么都不给」时兜底，代价是**标题相同的不同内容会被当成同一条**（例如「今日早报」每天同名 → 只留一条）——所以只当兜底。
- **症状对照**：键选错的表现是「刷新了但条目数不涨」或「同一条重复出现」；预览里会显示前 5 条算出来的键值，一眼可辨。
- ⇒ **不需要你在界面上做决定**，自动按上面的顺序走；只把「用了哪一级」显示出来即可。

### 4.4 接口

| 接口 | 用途 |
|---|---|
| `GET/POST/PATCH/DELETE /api/mcp/servers` | 连接管理（照本项目的 handler + swag 注解规范） |

| 建源 | 复用既有 `POST /api/feeds`，多带 `sourceType=mcp` + `mcpConfig` |

改完 `PATH="$HOME/go/bin:$PATH" make gen` + `swag init`。

### 4.5 UI（都在 AI 栏）

- AI 设置栏新增「**MCP 服务**」段：列表（名称 / 传输 / 连接状态 / 工具数 / `lastError`）+ 预设卡片（照 Folo 的形态）+ 新建/编辑。
- 每条连接一个用途标记：**仅 AI 用** / **用于 Feed** —— 同一份连接两种用途并存。
- 「+ 新建 MCP 订阅」向导：选服务 → 选工具或资源 → 字段映射（自动预填，可改）→ **预览前 5 条** → 建成**普通订阅行**（进第一栏、可进文件夹、可被规则/视图作用）。

## 五、出向：Krss 作为 MCP 服务器

**价值**：让 Claude Code / Codex / Hermes 这类 agent 直接读你的阅读器（「帮我总结今天未读的少数派」「搜我库里关于 Postgres 的条目」），而不用你做数据搬运。
**自洽性**：与入向共用同一套 MCP 底座；而且**我们自己控制返回形状，所以出向没有「映射」问题**。

### 5.1 暴露面（分只读 / 可写两组）

**只读（第一版就够）**
- tools：`list_feeds`（含文件夹/未读数）、`list_entries`（feedId / viewId / unreadOnly / starredOnly / limit）、`search_entries`（复用既有中文 LIKE 子串搜索）、`get_entry`（含正文）
- resources：`krss://feed/<id>`（该源最新条目 markdown）、`krss://entry/<id>`（单条正文）、`krss://unread`（未读列表）—— resource 自带 `uri`，正好对上 agent 的用法

**可写（默认关，需显式开启）**
- `mark_read` / `star_entry` —— 参考 Folo 的做法：`MCPService.enabled` 那种**逐连接开关**；危险动作按 MCP 规范的 `annotations` 标注。

### 5.2 鉴权与安全

- 传输：`streamable-http`，端点 `/mcp`（与既有 API 同源，复用 echo 路由）。
- 鉴权：**长期 token**（不要复用登录 JWT —— 那是短期的）；token 存 `settings` KV，生成时只显示一次，库里只存哈希。
- 默认**只读**；写操作单独开关；所有调用写日志（MCP 规范也要求 clients 侧做审计）。
- 只暴露该账号自己的库（单人自用，没有多租户问题）。

## 九、风险与坑

1. **凭据**：Header / token / OAuth 凭据属敏感数据 —— 照代理密码的做法**掩码**，**不进日志**（本项目已有 `redactNotifyTarget` 这类先例）。
2. **出网必须走统一网络层**：MCP 调用要走 `network.ClientFactory`（继承代理设置与 11-20 的超时/并发），别自己 `http.Get`。
3. **工具返回不是稳定 RSS**：字段可能变、可能分页 —— 映射失败要**明确写进该源的 `last_error`**（现有行内红字机制能用），**不许静默出空条目**。
4. **别加缓存**：与 14-2 同一条规矩 —— 设置改了要立刻生效，不要重启才生效。
5. **OAuth 是本批最大的工程量**（发现 + DCR + PKCE + 回调 + token 刷新 + 存储）：**回调取当前 origin** 是让远程部署也能用的关键；实现时不要写死 localhost。
6. **分页**：第一版按「每次取一页 + 可选追历史（页数/条数双上限）」；**首次接入绝不允许一次灌几千条**。
7. **写操作（出向）要先只读**：agent 误标已读/误加星是真实风险。
