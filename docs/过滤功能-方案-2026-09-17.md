# 过滤 / 自动化（Automation）功能调研与方案

_2026-09-17 · v2（补 MrRSS 参考后续修订） · 只做调研与方案，未动代码_

## 0. 结论先行

「按条文单独设置」和「像 Folo 那样做总体自动化」**不是二选一，而是同一个东西的两个入口**：

- 引擎只有一套 —— **规则（rule）= 作用域 + 条件 + 动作**；
- 「条文式」= 用 scope 把规则钉死在某个订阅/分类（入口：该订阅右键「新建规则」）；
- 「总体自动化」= 同一批规则在设置页统一列表管理（入口：设置 → 自动化）。

所以推荐：**一套规则引擎，每条规则自带 scope（全部 / 分类 / 订阅），两个入口（订阅右键、设置页）**。这是 Inoreader 的三段式（When 范围 → If 条件 → Then 动作）＋ Folo 的动作集 ＋ 我们已有的「跟随全局/覆盖」三态习惯。

执行时**只改自己数据库里的标记**（挂在抓取入库之后跑），前端只做「编辑 + 预览 + 回看」，不做渲染期过滤 —— 后者会破坏分页与未读计数。

## 1. 需求前提

现状（Gist 后端，`app/backend`）：

| 事实 | 出处 |
|---|---|

| feeds 有 `type`(article/picture/notification/social)、`folder_id`、`auto_translate`、`auto_summary`、`reader_mode` | 同上 + migration 19/20 |
| 条目列表接口支持 `feedId/folderId/contentType/unreadOnly/starredOnly/hasThumbnail/limit/offset`，**无搜索、无标签过滤** | `internal/handler/entry_handler.go:127-190` |
| 抓取入库路径唯一：`refresh_service.saveEntries()`（ExistsByHash → CreateOrUpdate，**逐条、拿得到 ID**） | `internal/service/refresh_service.go:166` |
| 迁移是编号式（已到 20），配 `hasColumn()` 守卫 + `ALTER TABLE`；KV 表 `settings` 可存 JSON | `internal/db/migrations.go:91+` |

| **后端没有任何推送/出网通道**（无 ntfy/bark/telegram/webhook 实现；"notification" 只是内容类型） | 全仓 grep |

即：要做「静音」这类"入库但不出现在列表"的语义，需要**一个新的标记字段**（`read` 不够：无法区分"用户读过"和"被规则静音"，也就无法一键反悔）。

## 2. 五种做法的调研对比

| 方案 | 代表 | 规则形状 | 作用范围 | 动作 | 执行位置 | 优点 | 致命缺点 |
|---|---|---|---|---|---|---|---|
| A. 文本条文 | Miniflux / **Nextflux** | `字段=正则` 纯文本，多行 | 全局 + 每订阅（2.2.10+） | 仅 block（丢弃）/ keep（只留） | 服务端抓取时，block 不入库 | 实现最省、正则强、顺序语义清晰（全局block→订阅block→全局keep→订阅keep，首个命中即停） | 不能"标已读/加星/通知/翻译"；要手写 RE2 正则；无命中反馈；Nextflux 前端**不含过滤 UI**（只在订阅编辑里给四个规则输入框），执行全在 Miniflux 服务端 |
| B. 规则引擎 | **Folo** | 一条规则 = When（全部源/自定义过滤）+ Then（可叠加多动作） | 弱：没有"这个源/这个文件夹"的一等公民，只能写进条件 | summary、translation、readability、view source、notification、**silence、block**、rewrite rules、webhooks | 服务端 | 动作集最丰富，正好覆盖我们已有的 AI 翻译/摘要；规则卡三段式 UI 成熟；可 JSON 导入导出 | 范围概念弱；无干跑预览 |
| C. 三段式引擎 | Inoreader | **When 范围（全部/文件夹/订阅）→ If 条件（ALL/ANY+正则）→ Then 动作** | 文件夹/订阅是一等公民 | 标已读/加星/打标签/通知/邮件/webhook/Read later/摘要/翻译/加笔记 | 服务端 | 范围语义最贴合"条文 vs 总体"；**命中计数 + 最近 100 条命中日志**；可从文件夹/订阅/文章右键建规则 | 打标签依赖我们没有的标签体系 |
| D. 训练式 | NewsBlur | 隐式 👍/👎 分类器（作者/标签/标题/正文/URL/站点），三态 Focus/Unread/**Hidden** | 订阅/分类/全局 | 只有高亮/常态/隐藏 | 服务端 | 体验最轻；有统一管理页（批量/搜索/筛选）；2026-04 起有自然语言与图片分类器 | 分类器多了心智爆炸、不可解释"为什么被隐藏" |
| **E. 双轨（规则引擎 + 保存筛选）** | **MrRSS** | 规则 = 名称 + 启用 + 条件链（每条件自带 `and/or` 与 `negate`）+ 多动作 + 顺序位 | 无独立 scope，"范围"写成条件（feed_name / feed_category / feed_tags / feed_type） | favorite/unfavorite、hide/unhide、mark_read/mark_unread、read_later/remove_read_later（**4 对正反动作**） | **入库后**批量跑，只改标记 | 条件字段极宽（含 has_summary / has_translation / has_image / has_audio / has_video、源月产文量、源最近报错状态）；正反成对动作让"例外规则"天然可表达；规则 JSON 导入导出；另有**保存筛选**（侧栏视图筛选）独立轨道 | 无干跑预览；无命中计数/日志；规则整包塞在 settings KV 的一行 JSON 里，难做索引与审计 |

补充：FreshRSS 介于 A 与 C 之间 —— 搜索语法（`intitle:`/`intext:`/`author:`/`#tag`/`date:`）＋ 订阅级「自动标已读 / 自动加星」两个动作，并可把查询存成"用户查询"当筛选视图；它**没有**通用规则引擎。

> 出处：Miniflux 官方规则文档；Folo wiki + 源码 `modules/action/*` + deepwiki；Inoreader blog/help；NewsBlur 功能页与 2026-01/04 博文；**MrRSS 源码**（`internal/rules/engine.go`、`internal/feed/fetcher.go:364-383`、`frontend/src/composables/rules/useRuleOptions.ts`、`frontend/src/types/filter.ts`、`components/modals/rules/*`）。

**取舍**：A 太窄（只有丢或留）、D 太重（分类器状态机 + 不可解释）。**B 的动作集 + C 的范围与审计 + E 的执行时机与正反语义 + 我们自己的后端条件**，是最贴合本项目的组合。

## 3. 推荐方案（v2 修订）

### 3.1 数据模型

新增迁移 21（沿用编号式 + 守卫写法）：

```sql
CREATE TABLE IF NOT EXISTS filters (
  id INTEGER PRIMARY KEY,              -- snowflake
  name TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1,
  position INTEGER NOT NULL DEFAULT 0, -- 匹配顺序：自上而下，首个命中即停
  scope_type TEXT NOT NULL DEFAULT 'all',   -- all | folder | feed
  scope_id INTEGER,                          -- folder_id / feed_id，NULL 表示全部
  conditions TEXT NOT NULL,                  -- JSON，见下
  actions TEXT NOT NULL,                     -- JSON，见下
  match_count INTEGER NOT NULL DEFAULT 0,
  last_matched_at TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_filters_scope ON filters(scope_type, scope_id);

-- 审计/反悔用，只保留最近 N 千条
CREATE TABLE IF NOT EXISTS filter_matches (
  id INTEGER PRIMARY KEY, filter_id INTEGER NOT NULL, entry_id INTEGER NOT NULL,
  actions TEXT NOT NULL, created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_filter_matches_entry ON filter_matches(entry_id);

ALTER TABLE entries ADD COLUMN muted INTEGER NOT NULL DEFAULT 0;  -- 被规则静音（可回看）
ALTER TABLE entries ADD COLUMN filter_id INTEGER;                 -- 最后命中的规则（"为什么看不到这条" + 一键反悔）
```

> MrRSS 证明「整个规则集塞进 settings KV 的一行 JSON」也能跑（`db.GetSetting("rules")`）。我们仍建议建表：要命中计数、要审计、要按 scope 取规则，而这些正是"误伤了能不能查出来、能不能反悔"的前提。

**条件 JSON**（平铺链，每条自带 `logic` 与 `negate`，照 MrRSS —— 比 Folo 的嵌套组更好实现也够用）：

```json
[
  {"logic":null,"negate":false,"field":"title","operator":"contains","value":"RT @"},
  {"logic":"or","negate":true,"field":"content","operator":"regex","value":"(?i)\\b(sponsored|推广)\\b"}
]
```

字段（全部可从现有数据取到）：`title` `content` `author` `url` `published_at` `feed_title` `feed_url` `feed_type` `folder` `has_thumbnail` `word_count` `is_read` `is_starred` `is_muted`
操作符：`contains` `exact` `regex` `before` `after` `older_than`(max-age，如 30d) `is_future` `is_empty` `is_not_empty`（+ `negate` 取反）

**动作 JSON**（**正反成对**，照 MrRSS）：

```json
{"mute":false,"unmute":false,"markRead":false,"markUnread":false,
 "star":false,"unstar":false,"keepOnly":false,
 "translate":false,"summary":false,"notify":false,"webhooks":[]}
```

| 动作 | 语义 | 可逆 | 阶段 |
|---|---|---|---|
| `mute` 静音 | 入库、`read=1`、`muted=1`：不进未读、列表默认隐藏，可在"已静音"回看 | ✅ | P1 |
| `unmute` 取消静音 | 反动作：让上层规则静音过的内容重新出现（**例外规则的关键**） | ✅ | P1 |
| `markRead` / `markUnread` | 只动已读位（不隐藏） | ✅ | P1 |
| `star` / `unstar` | 自动收藏 / 取消收藏 | ✅ | P1 |
| `keepOnly` 只保留匹配 | 该 scope 内**不匹配**的按 `mute` 处理（=Miniflux 的 keep，做成动作而非第二种规则类型，少一个概念） | ✅ | P1 |
| `translate` / `summary` | 复用已有 AI 能力自动跑 | — | P2 |
| `notify` / `webhooks` | 推送 / 出网（**后端目前没有任何通道，需先定通道**） | — | P2 |
| `block` 屏蔽（不入库） | 永久丢弃、不可恢复 | ❌ | **P2 或不做**（MrRSS 干脆没有这个动作） |

### 3.2 执行位置与时序（v2 修订）

```
抓取 → 解析 → CreateOrUpdate（照旧，不动写入路径）
      → 规则引擎对刚入库的这批条目按 position 依次匹配
            命中第一条 → 应用其全部动作（含正/反）、写 filter_matches、计数
            未命中 → 不动
      → translate/summary/notify/webhook（P2，异步）
```

关键修订：**执行点从"入库前判定"挪到"入库后、只改标记"**。

- 好处一：不动写入路径，不干扰去重（`ExistsByHash`）、`CreateOrUpdate`、FTS 触发器；实现更干净。MrRSS 就是这么做的（`fetcher.go` 在 `SaveArticles` 之后重查这批条目再跑引擎）。
- 好处二：入库后跑，`filter_matches` 能直接拿到 entry ID（我们是逐条 CreateOrUpdate，不像 MrRSS 那样要"再查一遍最近 N 条"来补 ID）。
- 代价：被静音的条目仍然入库（占空间）。单用户自托管可接受；真要"不入库"，那是 P2 的 `block`，届时再把判定前移到 `saveEntries` 之前。

### 3.3 规则冲突语义（v2 修订，建议改这一条）

**自上而下（position）、首个命中即停、一条规则内可带多个动作（含正反成对）。**

- 依据：Miniflux（首个匹配停止）、MrRSS（`ApplyRulesToArticles` 注释明写 "only the first matching rule is applied, prevents conflicting actions from multiple rules"）都是这个语义；Folo 也把多动作塞进一条规则。
- 好处：可预测、可解释；用"顺序 + 反动作"就能表达**例外**（例：① 源=某某 → mute；② 源=某某 且 标题含"财报" → unmute），不必把否定写死在同一条件里。
- 代价：想"组合"（源级静音 + 该源的财经类加星）就得写进同一条规则；比"动作叠加 + 优先级"少一点灵活性，但心智成本低得多。
- 与 v1 的差别：v1 推荐"动作叠加 + priority 数值"，现改为**顺序位 + 首个命中**。UI 上就是上下拖拽排序，用户不必理解"优先级数字"。

### 3.4 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/filters` | 列表（含 match_count / last_matched_at / position） |
| POST | `/api/filters` | 新建 |
| PATCH | `/api/filters/:id` | 编辑 / 启停 / 调顺序 |
| DELETE | `/api/filters/:id` | 删除（可选顺带"把该规则静音的条目恢复未读"） |
| POST | `/api/filters/preview` | **dry-run**：传入规则体，按 scope 取最近 N 条（默认 200）跑一遍，返回命中条目 + 各动作影响数（"将静音 27 条 / 加星 3 条"） |
| POST | `/api/filters/revert` | 按规则/按条目撤销静音（依赖 filter_matches） |
| GET | `/api/filters/:id/matches` | 命中日志（对齐 Inoreader 的 rule log） |

`preview` 是这个方案里最值钱的一个接口：Folo 没有、Miniflux 没有、**MrRSS 也没有**。没有它，任何正则都会误伤一整个源。

### 3.5 UI（按紧凑高密度偏好）

- 设置 → 新增 **「自动化」** 标签页：
  - 顶部工具条：`+ 新建规则` ／ 总开关 ／ 导入导出 JSON（对齐 Folo/MrRSS）
  - 全宽规则表格：`启用开关 · 名称 · 范围 · 条件摘要 · 动作摘要 · 命中数 · 最近命中 · 顺序拖拽 · 编辑`
  - 规则编辑器收进 **Drawer**：① 范围（全部/分类/订阅）② 条件（行式 field×operator×value，行间是**可点击切换的 and/or 胶囊**，抄 MrRSS 的 `RuleLogicConnector`；每行带"取反"开关）③ 动作（正反成对，勾了正就禁用反）＋ 底部常驻「预览影响」
- 入口三处：
  1. 设置页「自动化」
  2. **订阅右键 →「为此订阅新建规则」**（预填 scope）
  3. **条目右键 →「按此条新建规则」**（用该条的作者/源/标题片段预填条件 —— NewsBlur 训练器精髓的轻量移植）
- 条目侧可解释性：命中静音的条目在"全部"视图显示细标签「已静音 · 规则名」，点开可「撤销静音」或「豁免这类内容」（转成一条例外规则）。
- 列表顶部过滤条：在现有 `星标/未读/全部` 胶囊旁加「已静音」入口（默认隐藏静音条目，可切"显示"）。

### 3.6 另一条轨：保存的筛选视图（P2，MrRSS 给的启发）

MrRSS 把"过滤"拆成两件事：**规则（自动化，动数据）** 与 **Saved Filters（视图筛选，不动数据，侧栏存栏位）**。我们原本只写了"已静音入口"这一小块，可顺势升级成 **保存筛选**（把当前范围 + 条件存成侧栏快捷入口，如"只看某源的未读技术文"）。它与规则共用同一套条件编辑器，代价很小。

### 3.7 与现有能力的复用

- 「跟随全局 / 覆盖」三态 → 规则的 scope 层（同一套 UI 语汇）
- AI 翻译/摘要（含订阅覆盖）→ P2 的动作，直接调已有 service
- 已有的 AI provider 基建 → P3 的「AI 条件」（"这条与我的关注相关吗"）与「自然语言建规则」（LLM 生成规则 JSON，再走 preview 确认）
- 备份三连 + `filter_matches` 审计 → 误伤可回滚

## 6. 风险与坑

- **分页与计数**：任何"渲染期过滤"都会让 `hasMore`（后端 limit+1 判页）与未读计数失真 —— 静音必须在写库时落 `read=1`。
- **幂等与回溯**：`CreateOrUpdate` 对已存在条目会走更新分支；规则挂在入库后会**追改老条目**（再次刷新命中即覆盖）—— 需明确"仅新条目生效"，或显式提供回溯按钮，二者不能含糊。
- **首个命中的副作用**：用户容易以为"多条规则都会生效"。UI 必须把顺序做成显式拖拽，并在规则卡上标注"命中后停止"。
- **正反动作的互斥**：同一条规则里勾了 `mute` 又勾 `unmute` 要拦；跨规则靠顺序决定胜负，不靠优先级数字。
- **正则语法**：Go 端是 RE2（同 Miniflux），无回溯、不支持 lookahead —— 前端正则校验必须与 RE2 对齐（用 Go 侧校验接口，别用 JS 正则糊弄）。
- **数据变更可回滚**：静音/标已读会改数据，依赖现有每日三备份 + `filter_matches` 审计。
- **AI 动作的成本**：P2 的 translate/summary 会按规则对整批新条目自动跑（一次刷新可能几十上百条），必须先定模型/语言/是否接管订阅级覆盖，并复用已有的限流与缓存。
