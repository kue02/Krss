# 过滤 / 自动化（Automation）功能调研与方案

_2026-09-17 · 只做调研与方案，未动代码_

## 0. 结论先行

「按条文单独设置」和「像 Folo 那样做总体自动化」**不是二选一，而是同一个东西的两个入口**：

- 引擎只有一套 —— **规则（rule）= 作用域 + 条件 + 动作**；
- 「条文式」= 用 scope 把规则钉死在某个订阅/分类（入口：该订阅右键「新建规则」）；
- 「总体自动化」= 同一批规则在设置页统一列表管理（入口：设置 → 自动化）。

所以推荐：**一套规则引擎，每条规则自带 scope（全部 / 分类 / 订阅），两个入口（订阅右键、设置页）**。这是 Inoreader 的三段式（When 范围 → If 条件 → Then 动作）＋ Folo 的动作集 ＋ 我们已有的「跟随全局/覆盖」三态习惯。

执行位置**必须放后端抓取入库时**（屏蔽不入库、静音即标已读），前端只做「编辑 + 预览 + 回看」，不做渲染期过滤 —— 后者会破坏分页与未读计数。

## 2. 四种做法的调研对比

| 方案 | 代表 | 规则形状 | 作用范围 | 动作 | 执行位置 | 优点 | 致命缺点 |
|---|---|---|---|---|---|---|---|
| A. 文本条文（Miniflux） | Miniflux / **Nextflux** | `字段=正则` 纯文本，多行 | 全局 + 每订阅（2.2.10+） | 仅 block（丢弃）/ keep（只留） | 服务端抓取时，block 不入库 | 实现最省、正则表达力强、顺序语义清晰（全局block→订阅block→全局keep→订阅keep，首个命中即停） | 不能"标已读/加星/通知/翻译"；用户要手写 RE2 正则；没有规则命中反馈；Nextflux 前端本身**不含过滤 UI**（源码里只有订阅编辑的四个规则输入框，执行全在 Miniflux 服务端） |
| B. 规则引擎（Folo 自动化） | Folo | 结构化：一条规则 = When（全部源 / 自定义过滤）+ Then（可叠加多动作） | 主要"全部"，条件里可限定 feed | summary、translation、readability、view source、notification、**silence(=标已读)、block**、rewrite rules（字符串替换）、webhooks；可多条 | 服务端（账号体系） | 动作集最丰富，正好覆盖我们已有的 AI 翻译/摘要；配置可 JSON 导入导出；规则卡 UI 成熟（三段式 + 动作时间线） | 作用域概念弱（只有"全部/自定义条件"），没有"这个文件夹/这个源"的一等公民；无 dry-run，不知道会误伤什么 |
| C. 三段式规则引擎（Inoreader） | Inoreader | **When 范围（全部/文件夹/订阅）→ If 条件（可 ALL/ANY，支持正则）→ Then 动作** | 一层就到位（文件夹/订阅是一等公民） | 标已读、加星、**打标签**、通知、邮件、Webhook、Read later、生成摘要、翻译、加笔记、送第三方 | 服务端 | 范围语义最贴合"条文 vs 总体"的诉求；**有规则命中计数 + 最近 100 条命中日志**；可从文件夹/订阅/文章右键直接"创建规则" | 打标签依赖标签体系（我们没有）；商业功能思路偏重订阅制 |
| D. 训练式（NewsBlur Intelligence Trainer） | NewsBlur | 隐式：点 👍/👎 生成分类器（作者/标签/标题/正文/URL/站点），三态 Focus / Unread / **Hidden** | 订阅 / 分类 / 全局 | 只有"高亮 / 常态 / 隐藏"三态 | 服务端 | 体验最轻（不用想规则怎么写）；有统一管理页（批量编辑/搜索/按类型筛选）；2026-04 起有自然语言与图片分类器（LLM） | 300+ 分类器后心智负担爆炸；不可解释"为什么被隐藏"；要维护分类器与评分状态 |

补充：FreshRSS 介于 A 与 C 之间 —— 搜索语法（`intitle:`/`intext:`/`author:`/`#tag`/`date:`）＋ 订阅级「自动标已读 / 自动加星」两个动作，并可把查询存成"用户查询"当筛选视图；它也**没有**通用规则引擎。

**取舍**：A 太窄（只有丢或留）、D 太重（分类器状态机 + 不可解释）。**B 的动作集 + C 的范围与审计 + 我们的后端条件**，是最贴合本项目的组合。

## 3. 推荐方案

### 3.1 数据模型

新增迁移 21（沿用编号式 + 守卫写法）：

```sql
CREATE TABLE IF NOT EXISTS filters (
  id INTEGER PRIMARY KEY,              -- snowflake
  name TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1,
  priority INTEGER NOT NULL DEFAULT 0, -- 数值大的先执行
  scope_type TEXT NOT NULL DEFAULT 'all',   -- all | folder | feed
  scope_id INTEGER,                          -- folder_id / feed_id，NULL 表示全部
  match_mode TEXT NOT NULL DEFAULT 'all',    -- all(=AND) | any(=OR)，顶层
  conditions TEXT NOT NULL,                  -- JSON，见下
  actions TEXT NOT NULL,                     -- JSON，见下
  match_count INTEGER NOT NULL DEFAULT 0,
  last_matched_at TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_filters_scope ON filters(scope_type, scope_id);

-- 审计/反悔用，只保留最近 N 千条
CREATE TABLE IF NOT EXISTS filter_matches (
  id INTEGER PRIMARY KEY, filter_id INTEGER NOT NULL, entry_id INTEGER NOT NULL,
  actions TEXT NOT NULL, created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_filter_matches_entry ON filter_matches(entry_id);

ALTER TABLE entries ADD COLUMN muted INTEGER NOT NULL DEFAULT 0;  -- 被规则静音
ALTER TABLE entries ADD COLUMN filter_id INTEGER;                 -- 最后命中的规则（供"为什么看不到这条"与一键反悔）
```

> 为什么不用 `settings` KV 存 JSON：规则要按 scope 索引、要被执行引擎遍历、要记命中数，"表"才是正解；KV 只适合"自动化总开关"这类单例。

**条件 JSON**（数组即 OR，数组内的对象即 AND —— 与 Folo 的组语义一致、但不引嵌套爆炸）：

```json
[
  {"field":"title","operator":"contains","value":"RT @","regex":false},
  {"field":"content","operator":"matches","value":"(?i)\\b(sponsored|推广)\\b","regex":true}
]
```

字段（全部可从现有数据取到）：`title` `content` `author` `url` `published_at` `feed_title` `feed_url` `content_type` `folder` `has_thumbnail` `word_count`
操作符：`contains` `not_contains` `equals` `not_equals` `matches`(正则) `before` `after` `older_than`(max-age，如 30d) `is_future` `is_empty` `is_not_empty`

**动作 JSON**：

```json
{"block":false,"mute":true,"markRead":false,"star":false,"keepOnly":false,
 "translate":false,"summary":false,"notify":false,"webhooks":[]}
```

动作语义（这一节是设计的核心，写进 UI 帮助文案）：

| 动作 | 语义 | 可逆 | 阶段 |
|---|---|---|---|
| `mute` 静音 | 入库、`read=1`、`muted=1`：不进未读、列表默认隐藏，但可在"已静音"里回看 | ✅ 可一键反悔 | P1 |
| `block` 屏蔽 | **不入库**（省空间、计数干净） | ❌ 不可恢复 | P1（默认不选，UI 红字警告） |
| `markRead` 标已读 | 入库、`read=1`、`muted=0`：出现在"全部"里，不进未读 | ✅ | P1 |
| `star` 自动加星 | 命中即收藏（"只留重点"用） | ✅ | P1 |
| `keepOnly` 只保留匹配 | 该 scope 内**不匹配**的条目按 `mute` 处理（=Miniflux 的 keep 规则，但做成动作而非第二种规则类型，少一个概念） | ✅ | P1 |
| `translate` / `summary` | 复用已有 AI 能力自动跑 | — | P2 |
| `notify` / `webhooks` | 推送 / 出网（Gist 无推送通道，需另议） | — | P2 |

### 3.2 执行位置与时序

```
抓取 → 解析 → 逐条判定（scope 匹配到的规则，按 priority 降序） 
        ├─ block      → 跳过，不入库
        ├─ keepOnly   → 不匹配则转 mute
        ├─ mute/markRead/star → 写库时带上标记
        └─ translate/summary/notify/webhook → 写库后异步（P2）
```

挂载点：`refresh_service.saveEntries()`（`internal/service/refresh_service.go:166`）在 `CreateOrUpdate` **之前**判定，避免写完 FTS 再回退。

多条同时命中：**动作叠加**；同类动作冲突时取 `priority` 高者；`block` 优先级最高（命中即终止）。这与 Miniflux 的"首个匹配即停"不同 —— 我们按动作合并，更符合"自动化"心智，且规则间可组合（如"X 源全部静音" + "X 源里的财经类加星"）。

### 3.3 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/filters` | 列表（含 match_count / last_matched_at） |
| POST | `/api/filters` | 新建 |
| PATCH | `/api/filters/:id` | 编辑 / 启停 / 调优先级 |
| DELETE | `/api/filters/:id` | 删除（可选顺带"把该规则静音的条目恢复未读"） |
| POST | `/api/filters/preview` | **dry-run**：传入规则体，按 scope 取最近 N 条（默认 200）跑一遍，返回命中条目 + 各动作影响数（"将屏蔽 3 / 静音 27 条"） |
| POST | `/api/filters/revert` | 按规则/按条目撤销静音（依赖 filter_matches） |

`preview` 是这个方案里最值钱的一个接口：Folo 没有，Miniflux 没有。没有它，任何正则都会误伤一整个源。

### 3.4 UI（按紧凑高密度偏好）

- 设置 → 新增 **「自动化」** 标签页：
  - 顶部工具条：`+ 新建规则` ／ 总开关 ／ 导入导出 JSON（对齐 Folo）
  - 全宽规则表格：`启用开关 · 名称 · 范围 · 条件摘要 · 动作摘要 · 命中数 · 最近命中 · 编辑`
  - 规则编辑器收进 **Drawer**：三段式（① 范围：全部/分类/订阅 ② 条件：行式 field×operator×value，可切"正则" ③ 动作：复选 + 依赖项）＋ 底部常驻「预览影响」按钮
- 入口三处（Inoreader 最好用的点）：
  1. 设置页「自动化」
  2. **订阅右键 →「为此订阅新建规则」**（预填 scope）
  3. **条目右键 →「按此条新建规则」**（用该条的作者/源/标题片段预填条件，即 NewsBlur 训练器精髓的轻量移植）
- 条目侧的可解释性：命中静音的条目在"全部"视图显示一条细标签「已静音 · 规则名」，点开可「撤销静音」或「豁免这类内容」（把该条特征加成排除条件）。
- 列表顶部过滤条：在现有 `星标/未读/全部` 胶囊旁加「已静音」入口（默认隐藏静音条目，可切"显示"）。

### 3.5 与现有能力的复用

- 「跟随全局 / 覆盖」三态 → 规则的 scope 层（同一套 UI 语汇）
- AI 翻译/摘要（含订阅覆盖）→ P2 的动作，直接调已有 service
- 已有的 AI provider 基建 → P3 的「AI 条件」（"这条与我的关注相关吗"）与「自然语言建规则」（LLM 生成规则 JSON，再走 preview 确认）
- 备份三连 + 新 `filter_matches` 审计表 → 误伤可回滚

## 5. 待拍板决策点

1. **规则形状**：结构化条件（推荐，Folo/Inoreader 式）＋ 每个字段可切"正则模式"；还是照抄 Miniflux 的 `字段=正则` 文本框？（后者实现最省，但动作集被锁死在"丢/留"）
2. **屏蔽默认语义**：默认「静音（入库 + 标已读 + 可回看）」、`block`（不入库、不可恢复）需显式勾选 —— 是否同意？（Miniflux/Folo 的 block 是永久丢弃，我认为不适合作为默认）
3. **执行位置**：确认允许改 Go 后端（抓取入库时执行）。只做前端渲染过滤的话，未读计数与分页会失真，我不建议。
4. **scope 层级**：全局 / 分类 / 订阅 三层是否都要（推荐都要；分类层是 Miniflux 没有、Inoreader 有、而我们天然有文件夹的强项）
5. **新增字段**：`entries.muted` + `entries.filter_id`（推荐，换取"隐藏静音条目 / 一键反悔"）；还是复用 `read` 不加字段（改动小，但反悔只能靠 filter_matches 反查、且无法区分静音与已读）
6. **动作集 P1 边界**：`translate/summary/notify/webhook` 是否确认放 P2（P1 只做 block/mute/markRead/star/keepOnly）
7. **规则冲突语义**：动作叠加 + 优先级（推荐）vs Miniflux 的"首个匹配即停"
8. **是否需要"对历史条目回溯执行"**：默认只作用于新入库条目（推荐），回溯做成手动按钮

## 6. 风险与坑

- **分页与计数**：任何"渲染期过滤"都会让 `hasMore`（后端 limit+1 判页）与未读计数失真 —— 静音必须在写库时落 `read=1`。
- **幂等与回溯**：`CreateOrUpdate` 对已存在条目会走更新分支；规则若在更新路径生效，会追改老条目的 `muted` —— 需明确"仅新条目生效"，或显式提供回溯按钮，二者不能含糊。
- **FTS 触发器**：判定必须在 `CreateOrUpdate` 之前，否则先写 FTS 再丢弃，白跑且有脏数据风险。
- **block 不可逆**：UI 必须红字警告 + 建议"启用前强制跑一次预览"。
- **规则爆炸/互斥**：`priority` 与动作合并语义要写进帮助文案，否则半年后自己都看不懂为什么某条被静音。
- **正则语法**：Go 端是 RE2（同 Miniflux），无回溯、不支持 lookahead —— 前端正则校验必须与 RE2 对齐（可用 Go 侧校验接口，别用 JS 正则糊弄）。
- **数据变更可回滚**：静音/标已读会改数据，依赖现有每日三备份 + `filter_matches` 审计。
